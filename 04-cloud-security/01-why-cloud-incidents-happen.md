# 클라우드는 안전한데 왜 사고가 날까?  
## Security Misconfiguration으로 알아보는 클라우드 보안

클라우드 환경에서는 AWS와 같은 클라우드 서비스 제공자가 다양한 보안 기능을 제공한다.

그런데도 클라우드 환경에서 데이터 유출, 계정 탈취, 서버 침해와 같은 보안 사고는 계속 발생한다.

그렇다면 한 가지 의문이 생긴다.

> **클라우드 자체가 위험한 것일까?  
> 아니면 우리가 클라우드를 잘못 사용하고 있는 것일까?**

이번 글에서는 클라우드 보안에서 자주 발생하는 문제 중 하나인 **Security Misconfiguration(보안 설정 오류)**에 대해 정리해보려고 한다.

---

# 1. Security Misconfiguration이란?

Security Misconfiguration은 말 그대로 **시스템의 보안 설정이 적절하지 않은 상태**를 의미한다.

쉽게 생각하면,

> **잠겨 있어야 할 문이 설정 실수 때문에 열려 있는 상태**

라고 이해할 수 있다.

대표적인 예시는 다음과 같다.

- 외부에 공개되면 안 되는 클라우드 저장소가 Public으로 설정된 경우
- 서버의 SSH 포트가 인터넷 전체에 열려 있는 경우
- 사용자에게 필요 이상의 IAM 권한을 부여한 경우
- 운영 서버에서 Debug Mode를 활성화한 경우
- 기본 계정이나 사용하지 않는 기능을 그대로 유지한 경우
- 로그 및 보안 모니터링이 비활성화된 경우

이런 문제의 특징은 공격자가 반드시 복잡한 해킹 기술을 사용할 필요가 없다는 것이다.

이미 잘못 열려 있는 설정을 발견하는 것만으로도 공격이 시작될 수 있다.

---

# 2. 클라우드에서는 왜 설정 오류가 더 중요할까?

클라우드의 가장 큰 장점 중 하나는 **빠른 확장성과 편리한 관리**이다.

AWS에서는 몇 번의 클릭이나 API 호출만으로 서버, 데이터베이스, 네트워크, 스토리지 등을 생성할 수 있다.

하지만 이 편리함은 반대로 생각하면 **잘못된 설정 역시 매우 빠르게 적용될 수 있다는 의미**이기도 하다.

예를 들어 하나의 잘못된 설정이 Infrastructure as Code나 자동화 도구를 통해 여러 서버에 동시에 배포될 수도 있다.

또한 클라우드 리소스는 인터넷과 연결되는 경우가 많기 때문에 작은 설정 실수가 전 세계에 서비스나 데이터를 노출하는 결과로 이어질 수도 있다.

따라서 클라우드 환경에서는 단순히 서비스를 구축하는 것뿐만 아니라 **어떤 설정으로 구축했는가**가 매우 중요하다.

---

# 3. 클라우드 보안의 공동 책임 모델

클라우드 보안을 이해하기 위해서는 **Shared Responsibility Model, 공동 책임 모델**을 알아야 한다.

AWS를 사용한다고 해서 모든 보안을 AWS가 담당하는 것은 아니다.

AWS는 데이터센터, 물리 서버, 네트워크 장비 등 **클라우드 자체의 인프라 보안**을 담당한다.

반면 사용자는 자신이 생성하고 설정한 클라우드 리소스의 보안을 관리해야 한다.

예를 들면 다음과 같다.

AWS가 담당하는 영역은 물리 데이터센터, 서버 하드웨어, 글로벌 네트워크 인프라 등이다.

반면 사용자는 다음과 같은 부분을 관리한다.

- IAM 사용자와 권한
- Security Group
- S3 Bucket 접근 권한
- 애플리케이션 보안
- 데이터 암호화
- 계정 및 인증 관리

즉 AWS 인프라 자체가 안전하더라도 사용자가 S3를 외부에 공개하거나 관리자 권한을 무분별하게 부여한다면 보안 사고가 발생할 수 있다.

---

# 4. 대표적인 Security Misconfiguration 사례

## 4-1. Public으로 공개된 S3 Bucket

AWS S3는 파일을 저장할 수 있는 Object Storage 서비스다.

예를 들어 회사의 이미지, 로그, 백업 파일 또는 고객 데이터가 S3에 저장될 수 있다.

문제는 접근 권한을 잘못 설정했을 때 발생한다.

예를 들어 다음과 같이 모든 사용자에게 접근을 허용한다고 가정해보자.

```json
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "*"
}
```

`Principal: "*"`은 특정 사용자만 지정한 것이 아니라 광범위한 접근을 허용할 수 있다는 의미다.

중요한 데이터가 저장된 버킷이 Public으로 공개된다면 외부 사용자가 해당 데이터에 접근할 가능성이 생긴다.

따라서 일반적으로 S3는 **기본적으로 비공개 상태를 유지하고 필요한 대상에게만 접근 권한을 부여해야 한다.**

---

# 5. 모든 곳에 열린 Security Group

두 번째 사례는 Security Group이다.

Security Group은 AWS에서 EC2와 같은 리소스의 네트워크 접근을 제어하는 일종의 방화벽 역할을 한다.

예를 들어 다음 설정이 있다고 생각해보자.

```text
Port : 22
Source : 0.0.0.0/0
```

22번 포트는 일반적으로 SSH 접속에 사용된다.

그리고 `0.0.0.0/0`은 사실상 인터넷의 모든 IPv4 주소에서 접근을 허용한다는 의미다.

이 설정만으로 서버가 바로 해킹되는 것은 아니다.

하지만 공격자는 인터넷을 스캔하면서 해당 서버의 SSH 서비스가 열려 있다는 것을 발견할 수 있다.

이후 계정 정보 탈취, 무차별 대입 공격 또는 서비스 취약점 등을 이용한 추가 공격을 시도할 수 있다.

따라서 SSH나 RDP와 같은 관리 포트는 가능한 한 인터넷 전체에 공개하지 않고 **특정 IP, VPN 또는 안전한 관리 서비스를 통해 접근하도록 제한하는 것이 좋다.**

---

# 6. 과도한 IAM 권한

클라우드 보안에서 IAM은 매우 중요한 영역이다.

IAM은 간단하게 말하면,

> **누가 어떤 AWS 리소스에서 어떤 행동을 할 수 있는지 결정하는 시스템**

이다.

예를 들어 다음과 같은 IAM Policy가 있다고 생각해보자.

```json
{
  "Effect": "Allow",
  "Action": "*",
  "Resource": "*"
}
```

`Action: "*"`은 모든 작업을 의미하고,

`Resource: "*"`은 모든 리소스를 의미한다.

따라서 사실상 매우 강력한 관리자 수준의 권한이 될 수 있다.

처음에는 개발 편의를 위해 이런 권한을 부여할 수도 있다.

하지만 해당 사용자의 자격 증명이 탈취된다면 문제가 달라진다.

공격자 역시 그 계정과 동일한 권한을 사용할 수 있기 때문이다.

그래서 IAM에서는 **Least Privilege Principle, 최소 권한 원칙**이 중요하다.

즉,

> 필요한 사용자에게  
> 필요한 리소스에 대해  
> 필요한 작업만 허용한다.

라는 원칙이다.

---

# 7. Debug Mode와 상세 오류 메시지

Security Misconfiguration은 클라우드 인프라에서만 발생하는 것은 아니다.

애플리케이션 설정에서도 발생할 수 있다.

대표적인 사례가 운영 환경에서 Debug Mode를 활성화하는 것이다.

개발 과정에서는 Debug Mode가 매우 편리하다.

오류가 발생했을 때 프로그램의 내부 상태나 오류 원인을 자세하게 보여주기 때문이다.

하지만 운영 서버에서 이런 정보가 외부 사용자에게 그대로 노출되면 공격자에게도 유용한 정보가 될 수 있다.

예를 들어 다음과 같은 정보가 노출될 수 있다.

- 서버 내부 파일 경로
- 사용 중인 Framework
- Database 정보
- Stack Trace
- 환경 변수
- 내부 API 구조

따라서 개발 환경과 운영 환경의 설정을 명확하게 분리하는 것이 중요하다.

---

# 8. 보안 사고는 하나의 실수보다 '연쇄적인 실수'로 커진다

실제 보안 사고는 하나의 설정 오류만으로 발생하기보다는 여러 실수가 연결되면서 큰 사고가 되는 경우가 있다.

예를 들어 다음과 같은 상황을 생각해볼 수 있다.

```text
개발 편의를 위해 관리자 권한 부여
        ↓
S3 또는 서버가 외부에 노출
        ↓
Access Key 또는 계정 정보 노출
        ↓
공격자가 AWS 계정 접근
        ↓
높은 IAM 권한 사용
        ↓
다른 AWS 리소스로 공격 범위 확대
        ↓
데이터 유출 / 리소스 삭제 / 비용 발생
```

여기에 CloudTrail이나 보안 알림까지 설정되어 있지 않다면 공격 사실을 발견하는 데 더 많은 시간이 걸릴 수도 있다.

따라서 클라우드 보안에서는 사고가 발생한 뒤에만 대응하는 것이 아니라 **공격 과정의 연결고리를 미리 끊는 것이 중요하다.**

---

# 9. 왜 이런 설정 오류가 발생할까?

흥미로운 부분은 개발자나 운영자가 보안을 전혀 몰라서만 이런 문제가 발생하는 것은 아니라는 것이다.

실제 환경에서는 여러 현실적인 이유가 존재할 수 있다.

대표적으로 다음과 같다.

**빠른 개발과 배포**

서비스 출시 일정 때문에 우선 동작하게 만들고 보안 설정은 나중에 적용하는 경우가 발생할 수 있다.

**수동 설정**

관리자가 AWS Console에서 여러 리소스를 직접 설정하다 보면 실수가 발생할 가능성이 높아진다.

**과도한 권한**

권한 오류를 피하기 위해 관리자 권한을 부여하면 개발은 편해질 수 있지만 보안 위험은 커진다.

**책임 영역의 불분명함**

개발팀, 인프라팀, 보안팀 중 누가 특정 설정을 검토해야 하는지 명확하지 않을 수도 있다.

따라서 보안 문제를 단순히

> "누군가 실수했다."

라고 끝내는 것보다,

> **"사람이 실수해도 사고로 이어지지 않는 환경을 어떻게 만들 것인가?"**

를 고민해야 한다.

# 10. Secure Baseline 만들기

첫 번째 해결 방법은 **Secure Baseline**을 만드는 것이다.

쉽게 말하면 처음부터 안전한 설정을 기본값으로 사용하는 것이다.

예를 들어 다음과 같은 규칙을 만들 수 있다.

- S3 Public Access 기본 차단
- SSH/RDP 인터넷 전체 공개 금지
- IAM 최소 권한 적용
- Root Account 사용 최소화
- MFA 활성화
- 개발 환경과 운영 환경 권한 분리
- CloudTrail 및 로그 활성화
- 중요 데이터 암호화

이렇게 하면 매번 사람이 보안 설정을 판단해야 하는 상황을 줄일 수 있다.

즉,

> **사람이 항상 올바른 선택을 하기를 기대하기보다 시스템 자체를 안전한 방향으로 만드는 것**

이 중요하다.

---

# 11. IaC와 자동화를 통한 설정 관리

클라우드 환경이 커지면 수십 개 또는 수백 개의 리소스를 사람이 직접 확인하는 것은 현실적으로 어렵다.

그래서 Infrastructure as Code, 줄여서 **IaC**를 사용할 수 있다.

대표적으로 Terraform이나 AWS CloudFormation 등이 있다.

IaC를 사용하면 인프라 설정을 코드로 관리할 수 있다.

예를 들어 Security Group, IAM Policy, EC2 설정 등을 코드에 정의한 후 변경 이력을 Git으로 관리할 수 있다.

여기에 **Policy as Code**를 적용하면 특정 보안 기준을 만족하지 않는 설정을 자동으로 탐지하거나 배포 과정에서 차단할 수도 있다.

예를 들어,

```text
Terraform 작성
      ↓
보안 정책 검사
      ↓
S3 Public 발견
      ↓
배포 차단
```

과 같은 프로세스를 만들 수 있다.

보안 문제가 운영 환경에 배포된 다음 찾는 것이 아니라 **배포되기 전에 발견하는 방식**이다.

---

# 12. 지속적인 탐지와 모니터링

아무리 보안 설정을 잘 만들어도 실수를 100% 제거하기는 어렵다.

따라서 예방뿐만 아니라 **탐지**도 중요하다.

AWS에서는 여러 보안 서비스를 활용할 수 있다.

### AWS Config

AWS 리소스의 설정 상태와 변경 사항을 확인하는 데 사용할 수 있다.

예를 들어 Security Group이나 S3 설정이 보안 기준에 맞는지 확인할 수 있다.

### AWS CloudTrail

사용자가 AWS에서 수행한 API 활동을 기록한다.

누가 어떤 작업을 수행했는지 추적하는 데 중요한 로그가 된다.

### AWS Security Hub

여러 AWS 보안 서비스에서 발견된 보안 문제를 한곳에서 관리하는 데 도움을 준다.

### Amazon GuardDuty

AWS 환경에서 발생하는 의심스러운 활동을 탐지하는 서비스다.

결국 중요한 것은 한 번 안전하게 설정하고 끝내는 것이 아니라 **환경이 변경될 때마다 지속적으로 확인하는 것**이다.

---

# 13. 클라우드 보안 엔지니어 관점에서 생각해보기

이번 내용을 공부하면서 클라우드 보안 엔지니어가 단순히 AWS 서비스 이름을 많이 알고 있는 사람이 아니라는 생각이 들었다.

예를 들어 다음 설정을 발견했다고 가정해보자.

```text
SSH : 0.0.0.0/0
```

단순히

> "이 설정은 위험합니다."

라고 말하는 것보다,

왜 위험한지, 공격자가 어떻게 이용할 수 있는지, 그리고 어떤 방식으로 변경해야 하는지를 설명할 수 있어야 한다.

즉 클라우드 보안에서는 다음과 같은 사고 과정이 중요하다고 생각한다.

```text
현재 설정 확인
      ↓
위험 요소 발견
      ↓
공격 가능성 분석
      ↓
영향 범위 판단
      ↓
대응 방법 제시
      ↓
자동화 및 모니터링
```

특히 IAM, 네트워크, 로그, 클라우드 아키텍처 같은 기본 지식이 서로 연결되어 있다는 것도 알 수 있었다.

# 마무리

이번 내용을 정리하면서 클라우드 보안에서 중요한 것은 반드시 복잡한 해킹 기술만은 아니라는 것을 알게 되었다.

오히려 다음과 같은 사소한 설정이 실제 보안 문제의 시작점이 될 수 있다.

```text
S3 Public
Security Group 0.0.0.0/0
IAM Administrator 권한
Debug Mode 활성화
로그 미설정
```

그리고 이런 설정들은 대부분 개발이나 운영 과정에서 편의를 위해 만들어질 수 있다.

따라서 클라우드 보안에서는 다음 세 가지가 중요하다고 생각한다.

**1. 안전한 기본 설정을 만든다.**

사람이 매번 판단하기보다 Secure Baseline을 만들어 실수 가능성을 줄인다.

**2. 보안 설정을 자동으로 검증한다.**

IaC, Policy as Code, CI/CD 등을 활용해 잘못된 설정이 배포되기 전에 발견한다.

**3. 지속적으로 모니터링한다.**

AWS Config, CloudTrail, Security Hub, GuardDuty 등을 이용해 설정 변경과 이상 행동을 확인한다.

결국 이번 주제를 한 문장으로 정리하면 다음과 같다.

> **클라우드 보안은 단순히 공격을 막는 것이 아니라, 공격자가 이용할 수 있는 잘못된 설정을 만들지 않는 것에서부터 시작한다.**

이번 학습을 통해 앞으로 AWS를 공부할 때도 단순히 서비스를 사용하는 방법만 보는 것이 아니라,

**“이 서비스를 잘못 설정하면 어떤 보안 문제가 발생할 수 있을까?”**

라는 관점에서 함께 공부해봐야겠다는 생각이 들었다.
