## 들어가며

지난 시간에는 OSI 7계층을 공부하면서 데이터가 네트워크를 통해 전달되는 과정을 알아보았다.

이번에는 그중 **4계층인 전송 계층(Transport Layer)**에서 사용되는 대표적인 프로토콜인 TCP와 UDP를 자세히 알아보려고 한다.

TCP와 UDP는 모두 데이터를 목적지 프로그램까지 전달하는 역할을 하지만, 연결 방식과 데이터 전송을 관리하는 방법에서 큰 차이가 있다.

특히 TCP의 헤더 구조와 Flag, 3-way Handshake, 재전송 기능을 이해하면 실제 네트워크 패킷을 분석하거나 클라우드 환경에서 네트워크 문제를 해결할 때 도움이 된다.

이번 글에서는 TCP와 UDP를 택배 배송에 비유하면서 개념부터 실제 통신 과정까지 정리해보겠다.

## 1. TCP와 UDP란?

TCP(Transmission Control Protocol)와 UDP(User Datagram Protocol)는 OSI 7계층 중 **4계층인 전송 계층**에 해당한다.

3계층의 IP가 목적지 컴퓨터까지 데이터를 전달하는 역할을 한다면, 4계층에서는 Port 번호를 활용하여 해당 컴퓨터의 어떤 프로그램과 통신할지 구분한다.

예를 들어 IP 주소가 아파트의 주소라면, Port 번호는 아파트 안의 특정 호수를 구분하는 정보와 비슷하다.

### TCP — 확인하면서 보내는 택배

TCP는 **연결 지향형(Connection-oriented)** 프로토콜이다.

데이터를 전송하기 전에 상대방과 연결을 설정하고, 데이터가 올바른 순서로 전달될 수 있도록 관리한다.

택배를 보내고 상대방에게 잘 받았는지 확인한 다음, 문제가 발생하면 다시 보내는 방식과 비슷하다.

주요 특징은 다음과 같다.

- 통신 전 연결 설정
- 데이터 순서 관리
- ACK를 통한 수신 확인
- 손실된 데이터 재전송
- 흐름 제어 및 혼잡 제어
- 바이트 스트림(Byte Stream) 방식

### UDP — 별도 수신 확인 없이 보내는 택배

UDP는 **비연결형(Connectionless)** 프로토콜이다.

TCP와 달리 사전에 연결을 설정하지 않고 데이터그램을 전송한다.

택배를 보내되 기본적으로 상대방이 받았는지 별도로 확인하거나 재배송하지 않는 방식과 비슷하다.

주요 특징은 다음과 같다.

- 사전 연결 설정이 필요하지 않음
- 기본적인 ACK 기능이 없음
- 재전송을 자체적으로 수행하지 않음
- 전송 순서를 보장하지 않음
- 간단한 헤더 구조
- 데이터그램의 메시지 경계 유지

여기서 중요한 점은 **TCP가 무조건 빠르거나 UDP가 무조건 빠른 것은 아니라는 것**이다.

UDP는 기본적인 처리 구조가 단순하지만, 실제 성능은 네트워크 환경과 애플리케이션 설계에 따라 달라진다.

## 2. TCP와 UDP 비교

| 구분 | TCP | UDP |
|---|---|---|
| 연결 방식 | 연결 지향형 | 비연결형 |
| 전송 단위 | Segment | Datagram |
| 헤더 크기 | 최소 20Byte | 8Byte |
| 데이터 순서 | 보장 | 보장하지 않음 |
| ACK | 지원 | 기본 제공하지 않음 |
| 재전송 | 지원 | 기본 제공하지 않음 |
| 흐름 제어 | 지원 | 기본 제공하지 않음 |
| 혼잡 제어 | 지원 | 기본 제공하지 않음 |
| 데이터 형태 | 연속된 바이트 스트림 | 개별 데이터그램 |
| 주요 활용 | 웹, SSH, 파일 전송 | DNS, 실시간 통신, QUIC 기반 서비스 |

TCP는 데이터의 순서와 신뢰성이 중요한 환경에서 유용하다.

반면 UDP는 간단한 전송 구조가 필요하거나 애플리케이션에서 직접 전송 방식을 제어하려는 환경에서 유용하다.

다만 UDP 자체가 신뢰성 기능을 제공하지 않는다는 것이 UDP 기반 서비스도 신뢰성을 구현할 수 없다는 의미는 아니다.

## 3. TCP 헤더 구조

TCP는 데이터를 전송할 때 **헤더(Header)**라는 제어 정보를 함께 전달한다.

쉽게 말하면 택배 상자에 붙어 있는 운송장과 같다.

운송장에는 보내는 사람, 받는 사람, 배송 관리에 필요한 정보가 기록되어 있다.

TCP 헤더 역시 출발지와 목적지 Port, 데이터 순서, 수신 확인 번호 등 통신에 필요한 정보를 포함한다.

TCP 헤더는 최소 20Byte이며, 옵션이 추가되면 일반적으로 최대 60Byte까지 확장될 수 있다.

### TCP 헤더의 주요 필드

| 필드 | 크기 | 역할 |
|---|---|---|
| Source Port | 16bit | 출발지 Port 번호 |
| Destination Port | 16bit | 목적지 Port 번호 |
| Sequence Number | 32bit | 데이터 바이트의 순서 |
| Acknowledgment Number | 32bit | 다음에 받을 것으로 기대하는 바이트 번호 |
| Data Offset | 4bit | TCP 헤더 길이 |
| Reserved | 4bit | 예약 비트 |
| Flags | 8bit | 연결과 데이터 처리 제어 |
| Window Size | 16bit | 수신 가능한 데이터 양을 알림 |
| Checksum | 16bit | 전송 오류 검출 |
| Urgent Pointer | 16bit | 긴급 데이터 위치 관련 정보 |
| Options | 가변 | MSS, Window Scale 등의 추가 기능 |

헤더에서 특히 중요한 부분은 **Sequence Number, Acknowledgment Number, Flags**이다.

이 세 가지를 이해하면 TCP가 데이터를 어떻게 관리하는지 설명할 수 있다.

### Sequence Number와 ACK의 차이

Sequence Number는 TCP 바이트 스트림에서 데이터의 위치를 나타내는 번호다.

Acknowledgment Number는 다음에 받을 것으로 기대하는 바이트의 번호다.

예를 들어 다음과 같은 상황을 생각해보자.

```text
PC 1 → PC 2

SEQ = 1001
데이터 크기 = 1000Byte

PC 2가 데이터를 정상 수신

PC 2 → PC 1

ACK = 2001
```

PC 1이 1001번부터 2000번까지의 바이트를 전송했다면, PC 2는 다음에 2001번 바이트를 받고 싶다는 뜻으로 ACK 2001을 보낼 수 있다.

즉 **ACK 번호는 마지막으로 받은 바이트 번호가 아니라, 다음에 받을 것으로 기대하는 바이트 번호**라는 점이 중요하다.

## 4. TCP Flag란?

TCP Flag는 TCP 헤더에 포함되는 제어 비트다.

쉽게 말하면 택배 상자에 붙어 있는 **'배송 시작', '수령 확인', '배송 종료' 같은 상태 표시**라고 생각하면 된다.

TCP에서는 Flag를 이용해 연결을 설정하거나 종료하고, 데이터 처리를 제어한다.

### TCP의 8가지 Flag

| Flag | 의미 | 주요 역할 |
|---|---|---|
| SYN | Synchronize | 연결 설정 시 시퀀스 번호 동기화 |
| ACK | Acknowledgment | 확인 응답 번호가 유효함을 표시 |
| FIN | Finish | 송신자가 더 이상 보낼 데이터가 없음을 알림 |
| RST | Reset | 연결 재설정 |
| PSH | Push | 데이터를 수신 애플리케이션에 신속히 전달하도록 요청 |
| URG | Urgent | Urgent Pointer 필드가 유효함을 표시 |
| ECE | ECN Echo | 혼잡 통지 관련 정보 전달 |
| CWR | Congestion Window Reduced | 혼잡 통지에 대한 대응 표시 |

이 중 초보자가 가장 먼저 이해해야 할 Flag는 네 가지다.

**SYN — "통신을 시작하자!"**

TCP 연결을 설정할 때 사용한다.

**ACK — "여기까지 받았어!"**

상대방이 전송한 데이터에 대한 확인 응답과 관련된다.

**FIN — "나는 더 보낼 데이터가 없어!"**

TCP 연결을 정상적으로 종료할 때 사용한다.

**RST — "이 연결을 재설정하자!"**

정상적인 종료 절차와 달리 연결을 재설정하는 데 사용한다.

## 5. TCP 연결 과정 — 3-way Handshake

TCP는 데이터를 전송하기 전에 연결을 설정한다.

이 과정을 **3-way Handshake**라고 한다.

쉽게 이해하기 위해 두 사람이 전화 통화를 시작하는 상황을 생각해보자.

첫 번째 사람은 통화할 준비가 되어 있는지 물어본다.

두 번째 사람은 준비되었다고 응답하면서 상대방의 준비 상태도 확인한다.

마지막으로 첫 번째 사람이 응답하면서 통신에 필요한 상태를 동기화한다.

### 3-way Handshake 과정

```text
PC 1 (Client)                 PC 2 (Server)
     |                             |
     | -------- SYN -------------> |
     |       SEQ = 1000            |
     |                             |
     | <------ SYN + ACK --------- |
     |  SEQ = 5000, ACK = 1001      |
     |                             |
     | -------- ACK -------------> |
     |       ACK = 5001            |
     |                             |
     |       연결 설정 완료         |
```

**1단계: SYN**

클라이언트가 서버에 연결을 요청한다.

**2단계: SYN + ACK**

서버가 요청을 확인하고 자신의 시퀀스 번호를 포함하여 응답한다.

**3단계: ACK**

클라이언트가 서버의 응답을 확인하면서 연결이 설정된다.

여기서 SYN은 시퀀스 번호 공간을 1만큼 사용하기 때문에 초기 SEQ가 1000이면 다음 번호는 1001이 된다.

이러한 과정을 통해 양쪽은 서로의 초기 시퀀스 번호와 통신 상태를 확인한다.

## 6. TCP 데이터 전송과 제어 기능

TCP 연결이 설정되면 본격적인 데이터 전송이 시작된다.

이때 중요한 기능은 **흐름 제어(Flow Control)**와 **혼잡 제어(Congestion Control)**다.

### 흐름 제어 — 받는 사람의 처리 능력 고려

예를 들어 택배를 받는 사람의 창고에 10개의 상자만 들어갈 수 있다고 생각해보자.

그런데 보내는 사람이 한꺼번에 100개의 상자를 보내면 문제가 발생할 수 있다.

TCP의 흐름 제어는 수신자가 받아들일 수 있는 데이터 양을 고려하여 송신량을 조절하는 기능이다.

대표적으로 수신 윈도우(Receive Window)를 사용한다.

### 혼잡 제어 — 도로의 혼잡 상태 고려

이번에는 택배를 받는 사람의 창고는 충분히 크지만, 택배를 운송하는 도로가 막혀 있다고 생각해보자.

아무리 많은 택배를 보내도 도로가 혼잡하다면 오히려 전달이 지연될 수 있다.

TCP의 혼잡 제어는 네트워크 상태를 고려하여 데이터 전송량을 조절하는 기능이다.

정리하면 다음과 같다.

- **흐름 제어:** 받는 컴퓨터가 처리할 수 있는가?
- **혼잡 제어:** 네트워크가 감당할 수 있는가?

두 기능은 모두 안정적인 데이터 전송을 위해 중요하다.

## 7. TCP 연결 종료 — FIN과 ACK

TCP는 연결 설정뿐만 아니라 종료 과정도 관리한다.

일반적으로 정상적인 연결 종료를 설명할 때는 **4-way Handshake**를 사용한다.

```text
PC 1                           PC 2
 |                               |
 | ---------- FIN -------------> |
 |                               |
 | <--------- ACK -------------- |
 |                               |
 | <--------- FIN -------------- |
 |                               |
 | ---------- ACK -------------> |
 |                               |
 |          연결 종료             |
```

각 단계의 의미는 다음과 같다.

1. PC 1이 FIN을 보내 자신의 송신을 종료하겠다고 알린다.
2. PC 2가 ACK로 확인한다.
3. PC 2도 전송을 마치면 FIN을 보낸다.
4. PC 1이 ACK로 응답한다.

TCP는 양방향 통신이 가능하기 때문에 한쪽이 더 이상 데이터를 보내지 않더라도 반대 방향의 데이터 전송은 잠시 계속될 수 있다.

또한 실제 통신에서는 FIN과 ACK가 하나의 세그먼트로 함께 전달되기도 하므로 종료 과정이 반드시 독립적인 네 개의 세그먼트로만 구성되는 것은 아니다.

연결 종료 과정에서는 **TIME_WAIT** 상태도 중요하다.

이 상태는 마지막 ACK가 손실되었을 때 재전송에 대응하고, 이전 연결의 지연된 세그먼트가 새로운 연결에 영향을 주는 위험을 줄이는 역할을 한다.

## 8. TCP 재전송 기능 — 타임아웃(RTO)

TCP의 중요한 특징 중 하나는 손실된 데이터를 재전송할 수 있다는 것이다.

예를 들어 택배를 보냈는데 상대방에게 배송 완료 확인을 받지 못했다고 생각해보자.

보낸 사람은 일정 시간 기다린 뒤 택배가 전달되지 않았을 가능성을 고려하여 다시 보낼 수 있다.

TCP도 비슷한 방식으로 동작한다.

### Retransmission Timeout

RTO는 **Retransmission Timeout**의 약자로, 재전송 타임아웃을 의미한다.

```text
PC 1                         PC 2
 |                             |
 | -------- DATA ------------> |
 |                             |
 |       ACK 손실 발생          |
 | < - - - - X                 |
 |                             |
 |       RTO 만료              |
 |                             |
 | -------- DATA ------------> |
 |                             |
 | <--------- ACK ------------- |
```

위 그림에서는 데이터가 도착했더라도 ACK가 손실되어 송신자가 확인하지 못하는 상황을 가정했다.

송신자는 RTO가 만료되면 아직 확인받지 못한 데이터를 재전송할 수 있다.

수신자는 중복 데이터를 식별하여 바이트 스트림이 중복 전달되지 않도록 처리한다.

### RTO는 항상 같은 시간일까?

그렇지 않다.

RTO는 **RTT(Round Trip Time)**, 즉 데이터를 보내고 응답을 받는 데 걸리는 왕복 시간의 측정값과 변동성을 고려하여 계산된다.

또한 연속적으로 타임아웃이 발생할 경우 일반적으로 타임아웃 시간을 두 배로 늘리는 **Exponential Backoff(지수적 백오프)**를 적용한다.

이 방법은 네트워크가 혼잡할 때 반복적인 재전송이 혼잡을 악화시키는 상황을 줄이는 데 도움을 준다.

TCP는 타임아웃 외에도 중복 ACK 등 손실 징후를 활용하는 빠른 재전송 기능을 사용한다.

## 9. UDP 헤더 구조

UDP는 TCP에 비해 헤더 구조가 단순하다.

TCP의 헤더가 최소 20Byte인 반면 UDP의 헤더는 **8Byte**다.

UDP 헤더는 네 가지 필드로 이루어진다.

```text
  0              16              32 bit
  +---------------+---------------+
  |  Source Port  | Destination   |
  |               |     Port      |
  +---------------+---------------+
  |    Length     |   Checksum    |
  +---------------+---------------+
  |            Data ...           |
  +-------------------------------+
```

| 필드 | 크기 | 기능 |
|---|---|---|
| Source Port | 16bit | 출발지 Port 번호 |
| Destination Port | 16bit | 목적지 Port 번호 |
| Length | 16bit | UDP 헤더와 데이터의 길이 |
| Checksum | 16bit | 데이터 손상 여부 검출 |

UDP에는 TCP의 Sequence Number, Acknowledgment Number, Window Size, SYN/FIN 등의 연결 제어 필드가 없다.

따라서 구조가 단순하며 사전 연결 설정 없이 데이터를 전송할 수 있다.

다만 작은 헤더가 모든 상황에서 더 높은 전송 성능을 보장하는 것은 아니다.

## 10. TCP와 UDP의 Checksum 차이

이번 과제에서 중요하게 다룬 부분이 **Checksum(체크섬)**이다.

체크섬은 데이터가 전송되는 동안 손상되었는지 확인하기 위한 오류 검출 값이다.

쉽게 말하면 물건을 보내기 전에 확인한 검사 정보와, 받은 후 계산한 검사 정보를 비교하는 방식이다.

다만 체크섬은 오류를 검출하기 위한 기능이지 손상된 데이터를 직접 복구하는 기능은 아니다.

### TCP Checksum

TCP 체크섬은 IPv4와 IPv6 환경에서 필수다.

TCP 헤더와 데이터뿐 아니라 IP 주소 등을 포함한 의사 헤더(Pseudo-header) 정보도 계산에 사용한다.

### UDP Checksum

UDP는 IP 버전에 따라 차이가 있다.

| 구분 | TCP Checksum | UDP Checksum |
|---|---|---|
| IPv4 | 필수 | 생략 가능 |
| IPv6 | 필수 | 기본적으로 필수 |
| 목적 | 오류 검출 | 오류 검출 |
| 재전송 기능 | TCP에서 제공 | UDP 자체에는 없음 |

IPv4에서 UDP 체크섬은 0으로 표시하여 생략할 수 있다.

반면 IPv6에서는 UDP 체크섬이 기본적으로 필수이며, 일부 특수한 터널링 환경에 제한적인 예외가 존재한다.

**주의할 점은 체크섬과 암호화는 다르다는 것이다.**

체크섬은 우발적인 데이터 손상을 검출하는 기능이다.

공격자가 데이터를 위조하는 것을 방지하거나 통신 내용을 암호화하는 보안 기능은 아니다.

이러한 보호에는 TLS 등의 별도 보안 기술이 필요하다.
