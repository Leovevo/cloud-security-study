## 들어가며

지난 시간에는 FTP, SMTP, POP3, IMAP, ICMP 등 네트워크에서 사용하는 다양한 프로토콜을 공부했다.

이번 6주차에는 실무에서 자주 사용하는 **SSH, Telnet, HTTP, HTTPS, DNS**의 역할과 특징을 알아보려고 한다.

네트워크를 공부하면서 단순히 프로토콜의 이름과 포트 번호만 외우는 것보다, **왜 이런 프로토콜이 만들어졌으며 실제로 어떻게 동작하는지** 이해하는 것이 중요하다고 느꼈다.

이번 학습에서는 다음 세 가지 질문을 중심으로 정리했다.

1. SSH와 Telnet은 어떻게 원격 서버에 접속하며, 왜 SSH가 더 안전할까?
2. HTTP와 HTTPS는 어떤 차이가 있으며, HTTPS는 어떻게 통신을 보호할까?
3. DNS는 사람이 입력한 도메인 이름을 어떻게 실제 서버 주소와 연결할까?

## 1. OSI 계층에서 각 프로토콜의 위치

이번에 알아볼 프로토콜은 모두 주로 **OSI 7계층인 응용 계층(Application Layer)**에 속한다.

| 프로토콜 | 주요 역할 | 기본 포트 | 전송 방식 |
|---|---|---|---|
| SSH | 안전한 원격 서버 접속 | TCP 22 | TCP |
| Telnet | 텍스트 기반 원격 접속 | TCP 23 | TCP |
| HTTP | 웹 요청 및 응답 | TCP 80 | HTTP/1.1·2는 일반적으로 TCP |
| HTTPS | 암호화된 웹 통신 | TCP 443 | TLS 기반, HTTP/3는 QUIC/UDP |
| DNS | 도메인 이름 및 관련 정보 조회 | UDP/TCP 53 | UDP 및 TCP |

각 프로토콜은 서로 다른 목적을 위해 사용된다.

예를 들어 서버를 관리하려면 SSH를 사용하고, 웹사이트에 접속할 때는 HTTP나 HTTPS를 사용하며, 도메인 이름에 대한 정보를 조회할 때는 DNS를 사용한다.

## 2. SSH(Secure Shell)란?

SSH는 Secure Shell의 약자로, 원격 컴퓨터나 서버에 안전하게 접속하기 위한 프로토콜이다.

쉽게 설명하면 **멀리 떨어진 서버의 관리실에 보안 출입문을 통해 들어가는 것**과 비슷하다.

예를 들어 AWS EC2 인스턴스를 생성했다고 가정해 보자.

EC2는 AWS 데이터센터에서 실행되는 가상 서버이기 때문에, 실제 서버 앞에 앉아서 키보드를 사용할 수 없다.

이때 SSH를 사용하면 자신의 컴퓨터에서 원격 서버에 접속하여 명령어를 실행할 수 있다.

### SSH의 주요 특징

- 통신 내용을 암호화한다.
- 서버의 신원을 확인할 수 있다.
- 비밀번호나 공개키 기반 사용자 인증을 지원한다.
- 원격 명령어 실행 및 서버 관리가 가능하다.
- SFTP, SCP 등 SSH 기반 파일 전송 기능을 사용할 수 있다.
- 포트 포워딩과 터널링 기능을 제공한다.

SSH의 가장 중요한 특징은 **암호화를 통해 통신을 보호한다는 점**이다.

### 2-1. SSH의 연결 과정

SSH 접속 과정을 간단하게 정리하면 다음과 같다.

```text
내 컴퓨터                  원격 서버
    |                          |
    |------ TCP 연결 --------->| 22번 포트
    |                          |
    |<---- 키 교환·서버 인증 --->|
    |                          |
    |------ 사용자 인증 ------->|
    |                          |
    |<==== 암호화된 통신 ======>|
```

클라이언트는 먼저 서버에 연결한 뒤 암호화 알고리즘을 협상하고 서버의 호스트 키를 확인한다.

그다음 비밀번호 또는 공개키 인증 등을 통해 사용자 신원을 확인한다.

인증이 완료되면 암호화된 채널을 통해 명령어를 전달할 수 있다.

### 2-2. SSH 공개키 인증

SSH에서 자주 사용하는 인증 방식 중 하나는 공개키 인증이다.

공개키 인증은 다음 두 가지 키를 사용한다.

| 키 | 역할 |
|---|---|
| 공개키(Public Key) | 서버에 등록하여 사용자 인증에 활용 |
| 개인키(Private Key) | 사용자가 비밀리에 보관하는 키 |

쉽게 말하면 공개키는 자물쇠와 관련된 정보이고, 개인키는 본인만 가지고 있어야 하는 열쇠와 비슷하다.

실제 SSH 인증에서는 개인키 자체를 서버로 보내지 않고, 개인키를 보유하고 있음을 암호학적으로 증명한다.

**개인키가 유출되면 공격자가 해당 키를 악용할 수 있으므로 안전하게 보관해야 한다.**

### 2-3. SSH를 사용하는 대표적인 도구

| 도구 | 특징 |
|---|---|
| OpenSSH | 명령줄 기반 SSH 접속 도구 |
| PuTTY | Windows에서 널리 사용하는 SSH 클라이언트 |
| MobaXterm | SSH, SFTP 등 여러 기능을 제공하는 원격 접속 도구 |
| Termius | PC 및 모바일 환경에서 SSH 접속 관리 |
| WinSCP | SFTP를 통한 파일 전송에 주로 사용 |
| VS Code Remote-SSH | 원격 서버에서 개발 작업을 수행하는 확장 기능 |

예를 들어 AWS EC2 서버에 SSH로 접속하려면 다음 명령어를 사용할 수 있다.

```bash
ssh -i my-key.pem ubuntu@203.0.113.10
```

여기서 `my-key.pem`은 개인키 파일이고, `ubuntu`는 서버 사용자 계정이며, IP 주소는 예시 주소다.

## 3. Telnet이란?

Telnet은 원격 컴퓨터에 접속하여 텍스트 기반으로 명령을 주고받을 수 있도록 하는 오래된 프로토콜이다.

기본적으로 TCP 23번 포트를 사용한다.

Telnet은 SSH와 목적이 비슷하지만 중요한 차이가 있다.

**기본 Telnet은 통신 내용을 암호화하지 않는다.**

따라서 네트워크 통신을 가로챌 수 있는 공격자가 로그인 정보나 입력한 명령어를 확인할 위험이 있다.

### 3-1. SSH와 Telnet 비교

| 구분 | SSH | Telnet |
|---|---|---|
| 기본 포트 | TCP 22 | TCP 23 |
| 암호화 | 지원 | 기본적으로 지원하지 않음 |
| 사용자 인증 | 비밀번호·공개키 등 | 기본적으로 평문 로그인 |
| 서버 인증 | 호스트 키 검증 | 기본적으로 제공하지 않음 |
| 보안 수준 | 적절히 설정하면 안전한 원격 관리에 적합 | 도청·변조 위험 |
| 주요 활용 | Linux 서버, 클라우드 관리 | 레거시 장비·제한된 환경 |

### 3-2. 왜 Telnet 대신 SSH를 사용할까?

인터넷에서 서버에 접속한다고 생각해 보자.

Telnet은 내용을 보호하지 않은 채 통신하는 것과 비슷하다.

반면 SSH는 중요한 내용을 암호화해 전달한다.

따라서 현대적인 서버 관리에서는 일반적으로 SSH를 사용한다.

다만 SSH도 개인키 관리나 서버 인증을 소홀히 하면 보안 문제가 발생할 수 있다.

## 4. HTTP(Hypertext Transfer Protocol)란?

HTTP는 Hypertext Transfer Protocol의 약자로, 웹 브라우저와 웹 서버가 데이터를 주고받기 위한 통신 규칙이다.

우리가 웹사이트를 방문할 때 브라우저는 서버에 요청(Request)을 보내고 서버는 응답(Response)을 반환한다.

쉽게 말하면 **식당에서 주문하고 음식을 받는 과정**과 비슷하다.

- 브라우저: 주문하는 손님
- HTTP 요청: 주문서
- 웹 서버: 식당
- HTTP 응답: 주문한 음식과 처리 결과

### 4-1. HTTP 요청과 응답

```text
웹 브라우저                     웹 서버
     |                             |
     |------ GET /index.html ----->|
     |                             |
     |<----- 200 OK + HTML --------|
     |                             |
```

브라우저가 웹페이지를 요청하면 서버는 요청을 처리한 후 HTML 등의 데이터를 반환한다.

### 4-2. HTTP의 대표적인 메서드

| 메서드 | 역할 |
|---|---|
| GET | 리소스 조회 |
| POST | 데이터 제출·처리 요청 |
| PUT | 지정한 리소스를 생성하거나 교체 |
| PATCH | 리소스의 일부 변경 요청 |
| DELETE | 리소스 삭제 요청 |

### 4-3. HTTP 상태 코드

HTTP 응답에는 요청의 처리 결과를 나타내는 상태 코드가 포함된다.

| 상태 코드 | 의미 |
|---|---|
| 200 OK | 요청 성공 |
| 301 Moved Permanently | 영구 이동 |
| 400 Bad Request | 잘못된 요청 |
| 401 Unauthorized | 인증 필요 |
| 403 Forbidden | 접근 거부 |
| 404 Not Found | 리소스를 찾을 수 없음 |
| 500 Internal Server Error | 서버 내부 오류 |
| 503 Service Unavailable | 서비스 이용 불가 |

이러한 상태 코드는 웹 애플리케이션을 개발하거나 서버 장애를 분석할 때 자주 사용된다.

## 5. HTTPS(Hypertext Transfer Protocol Secure)란?

HTTPS는 HTTP 통신을 TLS(Transport Layer Security)로 보호하는 방식이다.

HTTP가 웹 통신의 규칙이라면, HTTPS는 그 통신에 **보안 기능을 적용한 방식**이라고 이해하면 된다.

### 5-1. HTTP와 HTTPS의 차이

| 구분 | HTTP | HTTPS |
|---|---|---|
| 주요 목적 | 웹 데이터 통신 | 보호된 웹 데이터 통신 |
| 일반적인 포트 | TCP 80 | TCP 443 또는 HTTP/3의 UDP 443 |
| 암호화 | 자체적으로 제공하지 않음 | TLS 사용 |
| 데이터 보호 | 도청·변조 위험 | 기밀성 및 무결성 보호 |
| 서버 신원 확인 | 별도의 보안 장치 필요 | TLS 인증서 검증 활용 |

예를 들어 공용 Wi-Fi에서 웹사이트에 로그인한다고 가정하자.

HTTP만 사용하는 경우 전송되는 정보가 보호되지 않아 도청이나 변조에 노출될 수 있다.

반면 HTTPS는 TLS로 통신을 보호하므로 전송 중 내용이 노출되거나 변경되는 위험을 크게 줄일 수 있다.

### 5-2. TLS란?

TLS는 네트워크 통신을 안전하게 보호하기 위한 보안 프로토콜이다.

주요 기능은 세 가지다.

**① 기밀성(Confidentiality)**

통신 내용을 암호화하여 제3자가 쉽게 읽지 못하도록 보호한다.

**② 무결성(Integrity)**

데이터가 전송 과정에서 임의로 변경되었는지 탐지할 수 있도록 한다.

**③ 인증(Authentication)**

인증서와 신뢰 체계를 활용해 접속 대상 서버의 신원을 검증한다.

### 5-3. HTTPS 연결 과정

```text
브라우저                        웹 서버
    |                              |
    |------- 연결 시작 ----------->|
    |                              |
    |<---- TLS 협상·인증서 --------|
    |                              |
    |------ 서버 인증서 검증 ------|
    |                              |
    |<==== 암호화된 HTTP 통신 ====>|
```

실제로는 TLS 버전과 HTTP 버전에 따라 연결 절차가 달라지지만, 핵심은 **통신을 시작하기 전에 신뢰할 수 있는 보안 연결을 수립한다는 것**이다.

단, HTTPS를 사용한다고 해당 웹사이트가 무조건 안전한 것은 아니다.

피싱 사이트나 악성 사이트도 HTTPS 인증서를 사용할 수 있기 때문이다.

### 5-4. HTTP/1.1, HTTP/2, HTTP/3의 차이

| 버전 | 특징 | 주요 전송 방식 |
|---|---|---|
| HTTP/1.1 | 널리 사용된 요청·응답 방식 | TCP |
| HTTP/2 | 하나의 연결에서 여러 스트림을 다중화 | TCP |
| HTTP/3 | QUIC을 사용해 연결과 스트림을 처리 | UDP 기반 QUIC |

특히 HTTP/3는 TCP 대신 QUIC을 사용한다는 특징이 있다.

QUIC은 UDP를 기반으로 하지만 자체적인 신뢰성 있는 전송, 혼잡 제어, 암호화 기능을 제공한다.

따라서 HTTP/3가 UDP를 사용한다고 해서 신뢰성이 없거나 암호화되지 않는 것은 아니다.

## 6. DNS(Domain Name System)란?

DNS는 Domain Name System의 약자로, 도메인 이름과 관련된 정보를 조회하는 분산형 시스템이다.

쉽게 말하면 **인터넷의 전화번호부**라고 생각하면 된다.

우리가 웹사이트에 접속할 때 보통 IP 주소 대신 도메인 이름을 입력한다.

예를 들어 `example.com`이라는 도메인으로 웹사이트에 접속한다고 생각해 보자.

컴퓨터는 서버와 통신하기 위해 IP 주소가 필요하다.

이때 DNS는 해당 도메인의 IP 주소와 같은 정보를 찾는 데 도움을 준다.

### 6-1. DNS 조회 과정

```text
사용자
  |
  | example.com 주소 요청
  v
DNS 재귀 리졸버
  |
  | 필요한 경우 조회
  v
루트 네임서버
  |
  v
TLD 네임서버
  |
  v
권한 네임서버
  |
  | DNS 레코드 응답
  v
DNS 재귀 리졸버
  |
  | IP 주소 등의 조회 결과
  v
사용자
```

DNS 조회를 수행하는 주요 구성 요소는 다음과 같다.

**재귀 리졸버(Recursive Resolver)**

사용자 대신 DNS 조회를 수행하는 서버다.

**루트 네임서버(Root Name Server)**

최상위 도메인에 대한 네임서버 정보를 안내한다.

**TLD 네임서버**

`.com`, `.net`, `.org` 등의 최상위 도메인과 관련된 정보를 제공한다.

**권한 네임서버(Authoritative Name Server)**

해당 도메인의 권한 있는 DNS 레코드를 제공한다.

실제 조회에서는 캐시를 활용할 수 있기 때문에 매번 모든 단계를 수행하는 것은 아니다.

### 6-2. DNS의 대표적인 레코드

DNS 레코드는 도메인과 관련된 여러 종류의 정보를 저장한다.

| 레코드 | 역할 |
|---|---|
| A | IPv4 주소 |
| AAAA | IPv6 주소 |
| CNAME | 다른 도메인 이름을 가리키는 별칭 |
| MX | 이메일을 수신할 메일 서버 정보 |
| NS | 해당 영역의 네임서버 정보 |
| TXT | 도메인 검증 및 이메일 보안 정책 등의 텍스트 정보 |

예를 들어 `example.com`의 A 레코드를 조회하면 해당 도메인에 설정된 IPv4 주소 정보를 확인할 수 있다.

### 6-3. DNS 캐시와 TTL

DNS에는 **캐시(Cache)**라는 개념이 존재한다.

같은 도메인을 조회할 때마다 매번 권한 네임서버까지 요청하면 많은 시간이 소요될 수 있다.

따라서 조회 결과를 일정 시간 저장해 두었다가 다시 활용한다.

DNS의 TTL(Time To Live)은 DNS 레코드의 캐시 보관 시간에 영향을 준다.

예를 들어 웹사이트의 IP 주소를 변경했는데 일부 사용자에게 이전 주소가 계속 표시되는 경우가 있다.

이는 DNS 캐시의 영향일 수 있다.

### 6-4. DNS 보안 기술

DNS와 관련된 대표적인 보안 기술은 DNSSEC, DoH, DoT가 있다.

**DNSSEC(DNS Security Extensions)**

DNS 응답의 출처와 무결성을 검증하는 데 사용한다.

DNS 응답이 위조되거나 변조되었는지 확인하도록 돕는다.

하지만 DNSSEC 자체가 DNS 질의 내용을 암호화하지는 않는다.

**DoH(DNS over HTTPS)**

DNS 질의를 HTTPS를 통해 전송한다.

**DoT(DNS over TLS)**

DNS 질의를 TLS로 보호된 연결을 통해 전송한다.

두 기술 모두 DNS 질의가 전송되는 구간의 기밀성 보호에 도움을 준다.

| 구분 | DNSSEC | DoH | DoT |
|---|---|---|---|
| 핵심 목적 | DNS 데이터 무결성·출처 검증 | DNS 질의 전송 암호화 | DNS 질의 전송 암호화 |
| 암호화 | DNS 질의 자체 암호화 X | HTTPS 사용 | TLS 사용 |
| 대표 포트 | DNS 자체 포트 사용 | TCP 443이 일반적 | TCP 853이 일반적 |

## 7. 실무에서 사용하는 네트워크 명령어

이번에 공부한 프로토콜은 실제 서버 운영과 장애 분석에도 사용된다.

### SSH 접속

```bash
ssh user@server.example
```

원격 서버에 SSH로 접속한다.

### SSH 버전 확인

```bash
ssh -V
```

설치된 SSH 클라이언트의 버전을 확인한다.

### HTTPS 응답 헤더 확인

```bash
curl -I https://example.com
```

웹 서버의 HTTP 응답 헤더와 상태 코드를 확인할 수 있다.

### DNS 주소 조회

```bash
nslookup example.com
```

해당 도메인의 DNS 조회 결과를 확인한다.

### DNS 레코드별 조회

```bash
dig example.com A
dig example.com MX
```

A 레코드나 MX 레코드와 같이 필요한 종류의 DNS 정보를 조회할 수 있다.

## 8. AWS 클라우드 환경과의 연관성

이번에 공부한 프로토콜은 AWS 환경에서도 매우 중요하다.

### 8-1. SSH와 EC2

AWS EC2에서 Linux 서버를 관리할 때 SSH를 사용할 수 있다.

이때 SSH 개인키와 사용자 계정을 적절히 관리하고 Security Group에서 TCP 22번 포트의 접근 대상을 필요한 범위로 제한해야 한다.

실제 운영 환경에서는 불필요하게 모든 IP 주소에 SSH 포트를 공개하지 않는 것이 중요하다.

### 8-2. HTTPS와 로드밸런서

AWS Application Load Balancer는 HTTPS 리스너와 TLS 인증서를 이용해 클라이언트의 암호화된 웹 연결을 처리할 수 있다.

또한 AWS Certificate Manager를 활용하면 지원되는 AWS 서비스에서 TLS 인증서를 관리하는 데 도움을 받을 수 있다.

### 8-3. DNS와 Route 53

Amazon Route 53은 AWS에서 제공하는 DNS 웹 서비스다.

도메인에 대한 DNS 레코드를 관리하고, 사용자가 서비스에 접근할 수 있도록 이름 조회를 지원한다.

클라우드 환경에서는 EC2, 로드밸런서, DNS, TLS 설정이 함께 작동하기 때문에 각 프로토콜의 역할을 이해해야 한다.

## 9. 이번 학습을 통해 느낀 점

이번 6주차에는 SSH, Telnet, HTTP, HTTPS, DNS의 특징과 차이점을 공부했다.

처음에는 여러 프로토콜의 이름과 포트 번호를 외우는 것이 중요하다고 생각했지만, 실제로 학습하면서 각 프로토콜이 해결하려는 문제가 다르다는 것을 알 수 있었다.

특히 SSH와 Telnet을 비교하면서 원격 접속에서 암호화와 인증이 왜 중요한지 이해할 수 있었다.

또한 HTTP와 HTTPS의 차이를 공부하면서 TLS가 통신 내용을 보호하고 서버 신원을 검증하는 역할을 한다는 점도 알게 되었다.

마지막으로 DNS의 조회 과정을 통해 평소 도메인 주소를 입력하는 단순한 행동 뒤에 여러 네임서버와 캐시가 동작한다는 사실을 이해할 수 있었다.

앞으로 클라우드 보안을 공부할 때도 단순히 서비스 설정 방법을 외우는 것이 아니라, **해당 서비스가 어떤 프로토콜을 기반으로 동작하고 어떤 보안 문제를 해결하는지** 함께 생각하며 학습할 것이다.

## 📌 6주차 핵심 3줄 요약

1. **SSH는 암호화된 원격 접속을 지원하며 Telnet은 기본적으로 평문 통신을 사용하기 때문에 현대적인 서버 관리에서는 SSH가 권장된다.**
2. **HTTP는 웹 브라우저와 서버 간의 요청·응답을 처리하고 HTTPS는 TLS를 이용해 통신을 보호하며, HTTP/3는 UDP 기반 QUIC을 사용한다.**
3. **DNS는 도메인 이름과 관련된 정보를 조회하는 시스템이며, DNS 레코드·캐시·DNSSEC·DoH 등의 개념을 이해하는 것은 네트워크 관리와 클라우드 보안의 기초가 된다.**
